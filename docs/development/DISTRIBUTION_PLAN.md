# Writing Room — Distribution Plan

> The plan this repository was built from, kept as background for contributors: why the project is shaped the way it is. The decisions it led to, and what each phase found, are in `DECISIONS.md`.

Status: Phases 0 to 5 done (ready to publish as a pre-release); Phase 6 (the author's cutover) rehearsed on a copy, the real chapter loop in the author's agent still to do; smoke tests are the last phase (2026-10-02) · Written 2026-10-01

Goal: a clean, harness-neutral Writing Room that other people can install and use, without losing the author's existing projects.

**Target harnesses at launch:** Claude Code, Devin (CLI and cloud), Hermes Agent (Nous Research), OpenCode.

---

## 1. Principles

1. **Skills are the unit of behaviour.** Everything the agents and slash commands do becomes an Agent Skills-format skill. No harness-specific frontmatter in the canonical source.
2. **Framework and project are separate.** The framework is installed and upgraded. The project (worlds, stories, styles) belongs to the author and is never overwritten.
3. **Scripts are an optimisation, never a requirement.** Each skill states a no-shell fallback.
4. **No subagent dependency.** Skills must run inline in a single session. Subagent isolation is a documented optional optimisation per harness.
5. **Existing projects keep working with zero required migration.** The v1 content layout is frozen (see §6).

---

## 2. Harness findings (checked 2026-10-01)

| Harness | Skill locations it reads | Guidance file | Notes |
|---|---|---|---|
| Claude Code | `.claude/skills/<name>/SKILL.md`, `~/.claude/skills/` | `CLAUDE.md` (can `@import` another file) | Also supports plugins, which can bundle skills. |
| Devin | `.agents/skills/` (recommended), `.claude/skills/`, `.github/skills/`, `.cursor/`, `.codex/`, `.windsurf/`, `.cognition/` | `AGENTS.md` | Scans repos on disk as they are cloned into a session. |
| OpenCode | `.opencode/skills/`, `.claude/skills/`, `.agents/skills/`, plus global `~/.config/opencode/skills/`, `~/.claude/skills/`, `~/.agents/skills/` | `AGENTS.md` | Walks up to the git worktree root. |
| Hermes Agent | `~/.hermes/skills/` (user-level; follows the agentskills.io standard) | `AGENTS.md` (verify) | Extra frontmatter allowed (`version`, `author`, `platforms`, `metadata`). Whether it can read a project-local skills directory must be verified. |

Consequences:

- **`SKILL.md` + folder-per-skill is the shared format.** All four accept it.
- **`.agents/skills/` covers Devin and OpenCode. `.claude/skills/` covers Claude Code, Devin and OpenCode.** So the plain-folder install needs only `.claude/skills/` for three of four harnesses; Hermes needs `~/.hermes/skills/`.
- **Name rules are the strictest common denominator (OpenCode):** `^[a-z0-9]+(-[a-z0-9]+)*$`, 1–64 chars, and must equal the directory name. All skill names follow this.
- **Frontmatter is limited to** `name`, `description`, and optionally `license`, `compatibility`, `metadata`. Hermes-specific extras go in `metadata`, not top-level, so the other harnesses ignore them cleanly.

Items still to verify before launch (do not assume): Hermes project-local skills and `AGENTS.md` handling; how Devin cloud sessions run bundled Python scripts; skill-description auto-trigger quality in each harness.

## 3. Repository layout (distributable)

```
writing-room/                        ← the framework repo
├── AGENTS.md                        ← neutral instructions (replaces Head role in CLAUDE.md)
├── CLAUDE.md                        ← one line: @AGENTS.md  (+ Claude-specific notes if any)
├── README.md  LICENSE  CHANGELOG.md
├── skills/                          ← CANONICAL SOURCE of every skill
│   ├── writing-room/                ← router/orchestrator (the former Head role) AND the runtime
│   │   ├── SKILL.md
│   │   ├── references/              ← conventions.md, layout.md
│   │   ├── scripts/                 ← Python, stdlib only: load_bible, load_world, query_position,
│   │   │                              create_snapshot, promote_chapter, wr_init, wr_migrate,
│   │   │                              wr_doctor, wr_resolve (+ wr_install in Phase 4)
│   │   └── shared/                  ← templates/ and craft/ (story structures, archetypes, tropes, styles)
│   ├── create-world/  create-style/  story-status/  promote-chapter/
│   ├── writing-assistant/  world-archivist/  story-ideator/  outliner/
│   ├── planner/  draft-writer/  reviewer/  draft-fixer/  story-analyzer/
│   └── <skill>/
│       ├── SKILL.md                 ← procedure only, short
│       └── references/              ← long material, loaded on demand
├── tests/  tools/                   ← dev only, not installed
├── extras/lm_studio_ideator.py      ← optional, off the main path
├── examples/sample-project/         ← complete small project (generated by tools/build_sample.py)
└── .claude-plugin/plugin.json       ← Claude Code plugin manifest
```

**The runtime lives inside the `writing-room` skill.** Every harness installs skills as siblings, so any skill reaches the scripts, templates and shared references at `../writing-room/…` wherever skills are installed. This replaces the earlier idea of a root-level `shared/` reached by `../../shared`, which would break after installation. Skills call that directory `<WR>` (defined in `skills/writing-room/references/conventions.md`) and never hard-code `Writing_Room/`.

## 4. Agents → skills conversion

### 4.1 Mapping

| Current | New skill | Notes |
|---|---|---|
| `CLAUDE.md` (Head) | `writing-room` + `AGENTS.md` | Router: detects project, reports pipeline state, names the next skill. |
| `writing-assistant`, `world-archivist`, `story-ideator`, `outliner`, `planner`, `draft-writer`, `reviewer`, `draft-fixer`, `story-analyzer` | same names | Direct conversion. |
| `reviewer-consistency`, `reviewer-character` | **removed** | Already deprecated; merged into `reviewer`. |
| Commands: `create-world`, `create-style`, `story-status`, `promote-chapter` | same names, as skills | One concept instead of two. |

### 4.2 Required changes per skill

- Strip `model:` and `tools:`. State needs in prose ("works best with a strong prose model; needs file read/write; script use optional").
- Replace "invoke the X agent" with "follow the `x` skill". Delegation to another skill is a handoff the user or the router performs; never assume a subagent API.
- Use harness-neutral verbs ("read the file", "list files matching"), not tool names (`Glob`, `Grep`, `Read`).
- Replace the hard-coded `Writing_Room/...` tree with project-relative paths and the project-root rule (§5).
- Replace `[[wikilinks]]` with plain relative paths in skill text. Obsidian support stays a user-facing option in the docs.
- Every script call gets a fallback line: "If you cannot run commands, read these files in this order: …".
- Split large skills. `story-analyzer` (646 lines), `reviewer` (421), `world-archivist` (381): `SKILL.md` holds the procedure; review categories, formats and examples move to `references/` and are loaded only at the step that needs them.
- Descriptions are written for auto-triggering: what it does, when to use it, what it needs, what it outputs.

### 4.3 Pipeline contract

Each skill ends with an explicit **Next step** line (e.g. draft-writer → reviewer → draft-fixer → story-analyzer → promote-chapter) and the router skill repeats the order. Harnesses that cannot auto-chain still guide the user.

## 5. Framework vs. project, and project discovery

- **Project root** = the directory that contains `writing-room.toml` (small marker: `layout = 1`, optional `framework_min`, optional default world/style).
- **Legacy detection:** if no marker is found, a directory containing `worlds/` and `stories/` is treated as a layout-1 project root. This is what makes existing projects work unchanged.
- Scripts resolve the root by: `--root` flag → `WRITING_ROOM_ROOT` env var → walk up from the working directory. They never `chdir` to a fixed location.
- **Template and craft lookup order:** project `templates/` and `writing_concepts/` (if present) → framework `shared/`. Authors can override any template by dropping a file in their project; fresh projects need nothing copied.
- `wr_init.py` / the `writing-room` skill's "new project" step scaffolds: marker file, `worlds/`, `stories/`, `writing_concepts/styles/`, and a starter style copied from the framework.
- Samples ship under `examples/`, never inside a user's project directories.

## 6. Backwards compatibility (existing projects must keep working)

**Frozen layout v1** (what exists today, unchanged):

```
worlds/<World>/…            stories/<Story>/…
writing_concepts/styles/    templates/ (optional override)
stories/<Story>/{CONCEPT.md, OUTLINE.md, chapters/, current_chapter/, state/{Timeline.md, ACTIVE_SCHEMES.md, STORY_FACTS.md, bible/}}
```

Rules:

1. **No file moves, no renames of user content** in this release. A skill that cannot find the new location falls back to the old one; there is no new location for content.
2. **Marker is optional.** An existing project works as-is via legacy detection. `wr_migrate.py` only adds `writing-room.toml` and, optionally, removes framework files that are now provided by the framework install.
3. **`wr_migrate.py` is non-destructive:** dry-run by default, requires a clean git tree (or makes a backup copy), prints exactly what it will do, and is idempotent.
4. **Format changes are versioned.** Any future change to a file format (e.g. `ACTIVE_SCHEMES.md`, `STORY_FACTS.md`, snapshot manifests) bumps `layout` in the marker, and `wr_migrate.py` handles it. Skills check `layout` and refuse with a clear message rather than guessing.
5. **Script CLI compatibility:** existing flags of `load_bible.py`, `query_position.py` and others (`--story`, `--world`, `--char`, `--loc`, `--faction`, `--no-schemes`, `--no-facts`, …) remain valid. Old `.sh` wrappers are kept for one release as thin shims, then dropped.
6. **Author's own migration:** the author's own projects move to a separate private project repo by pointing it at the framework; verified by running `story-status` and one full chapter loop on a copy before cutting over.
7. **Acceptance test:** a frozen copy of the current `Writing_Room/` content is kept as a fixture; every release must pass the script tests and a manual chapter loop against it.

## 7. Installation and per-harness support

One installer, `wr_install.py --harness <claude|devin|opencode|hermes|all> --scope <project|user>`. Default is copy (symlinks are unreliable on Windows). It never touches project content.

| Harness | Skills go to | Guidance file | Extra |
|---|---|---|---|
| Claude Code | `.claude/skills/` (project) or `~/.claude/skills/` | `CLAUDE.md` → `@AGENTS.md` | Also publishable as a plugin via `.claude-plugin/plugin.json`. |
| Devin | `.agents/skills/` (project) | `AGENTS.md` | Document the cloud-session case: repo contains skills, scripts run if the machine allows it. |
| OpenCode | `.agents/skills/` or `.opencode/skills/` (project), `~/.config/opencode/skills/` (user) | `AGENTS.md` | Reads `.claude/skills/` too, so a Claude install is already visible. |
| Hermes | `~/.hermes/skills/` (user) | `AGENTS.md` (verify) | Hermes-only metadata goes under `metadata:`; verify project-local discovery. |

The installer copies every folder under `skills/` as-is. Because the runtime (`scripts/`, `shared/`, `references/`) is inside `skills/writing-room/`, nothing is rewritten and relative paths stay valid. The alternative of inlining shared content into every skill is rejected, because it reintroduces the "update in 11 places" problem. Residual risk: a harness that installs one skill without its siblings breaks every `../writing-room/` reference; `wr_doctor` should detect this (Phase 4).

Per-harness limitations are documented in the README, not hidden. Claude Code is the reference platform; others are supported to the extent the smoke tests pass.

## 8. Scripts

- Python 3, stdlib only. Target 3.9+ (checked by `wr_doctor`), developed and tested on 3.11; 3.9 is untested.
- Root discovery as in §5. Add `--format json` wherever a skill parses the output.
- Add `wr_doctor.py`: checks project layout, marker, missing files, stale `SUMMARY.md`, and reports what each harness install can see.
- Remove duplicated `.sh` scripts after the shim release.
- Move `lm_studio_ideator.py` to `extras/` with its own README.
- Add pytest tests against `examples/sample-project/` and the legacy-layout fixture.
- Remove the committed `settings.local.json`; ship a documented minimal permissions snippet per harness instead.

## 11. Risks

- **Auto-triggering differs per harness.** A skill that fires reliably in Claude may not elsewhere. Mitigation: router skill plus explicit "next step" lines; test descriptions in each harness.
- **No subagents means more context in one session** (Draft Writer plus Reviewer plus Analyzer). Mitigation: `references/` splitting, scripts that load only the needed entities, and a documented "start a fresh session per stage" recommendation.
- **Script execution may be unavailable** (some Devin or sandboxed setups). Mitigation: a fallback in every skill; test with scripts disabled.
- **Shared-folder relative paths break if a harness copies a skill alone.** Mitigation: installer layout in §7 plus a `wr_doctor.py` check.
- **Private content in git history.** The working repository's early commits contain a sample that came from the author's own fiction (since replaced by an invented one). Mitigation: publish from a fresh repository made by `tools/export_public.py` (single initial commit, no history) and run `tools/check_public_clean.py --history` on it.
- **Third-party harnesses change quickly.** The table in §2 is a snapshot; re-verify before each release.
